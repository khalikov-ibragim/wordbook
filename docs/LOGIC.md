# Логика приложения — Wordbook

## Что это

Личный словарь-блокнот. Вводишь слово или фразу → приложение переводит
(EN→RU или RU→EN, направление определяется автоматически) → перевод сразу
закрепляется отдельной записью в списке. Дальше со списком можно работать:
менять статус, редактировать, удалять, искать, фильтровать.

## Определение направления перевода

Направление не выбирается вручную — оно вычисляется по тексту:

- Есть кириллица в строке → считаем, что это `ru`, переводим в `en`.
- Нет кириллицы → считаем `en`, переводим в `ru`.

Это грубая эвристика, но для двух языков её достаточно. Реализована
одинаково в двух местах: `backend/src/routes/translate.js` (на всякий
случай, если фронтенд обошли напрямую) и `frontend/app.js` (чтобы знать
направление ещё до ответа сервера — например, для офлайн-резерва).

## Цепочка перевода (порядок отказоустойчивости)

Когда пользователь нажимает «→», приложение пробует источники по очереди,
пока один из них не сработает:

1. **Онлайн-перевод (LibreTranslate).**
   Обычный случай, когда есть интернет. Даёт лучшее качество перевода,
   покрывает и слова, и фразы.
   → Если одиночное слово — параллельно сохраняется в серверный словарь
   (`dictionary`), чтобы в следующий раз не дёргать внешний API заново.

2. **Серверный словарь (`dictionary` в Postgres).**
   Срабатывает, если онлайн-API недоступен (сеть до интернета пропала,
   но телефон всё ещё достаёт до домашнего/рабочего сервера — например,
   по Wi-Fi). Работает только для одиночных слов, не для фраз — фраз в
   этой таблице просто нет.

3. **Офлайн-словарь на устройстве (IndexedDB, только фронтенд).**
   Последний рубеж — используется, когда до сервера вообще не достучаться
   (метро, самолёт, глухая зона). Тоже только одиночные слова. Небольшой
   набор (десятки тысяч самых частых слов), скачан заранее и живёт в
   браузере через `db.js` → `WordbookDB.lookupDeviceWord`.

Если ни один из трёх источников не дал перевод (обычно — офлайн + фраза,
которой раньше не было, либо слово есть в тексте, но его просто нет ни в
одном словаре — например, айтишный жаргон вроде `middleware`) — не
показывается тупиковая ошибка. Вместо этого под строкой ввода появляется
панель «впиши перевод сам»: пользователь вписывает перевод вручную, запись
сохраняется как обычно (`source: 'manual'`), при отсутствии сети — тоже
через очередь `pendingEntries`, как и запись из офлайн-словаря на
устройстве.

## Что происходит с записью после перевода

- Успешный перевод (через 1 или 2) сразу уходит на бэкенд:
  `POST /api/entries` → запись создаётся со статусом `learning` («учу»)
  и полем `source`, которое запоминает, откуда взялся перевод
  (`online` / `server_dict` / `device_dict`) — пригодится, если потом
  захочется отдельно проверять качество офлайн-переводов.
- Если сработал офлайн-словарь на устройстве (3), а сети до сервера нет —
  запись не отправляется сразу. Она кладётся в очередь `pendingEntries`
  в IndexedDB и помечается в интерфейсе как «офлайн, ждёт синка».
- Как только приложение снова видит сеть (`window.addEventListener('online')`),
  оно проходит по очереди и по одной отправляет записи на сервер
  (`syncPending()` в `app.js`). После успешной отправки запись убирается
  из локальной очереди и живёт уже только в Postgres, как обычная.

## Контекст (необязательное поле)

У записи есть необязательное поле `context` — предложение или фраза,
откуда взято слово (например, строка из документации). Полезно для
технической лексики, где смысл слова без окружения не всегда очевиден.
Раскрывается кнопкой «+ добавить контекст» под строкой ввода, редактируется
позже через «Изменить» вместе с переводом.

## Приём текста из других приложений (Web Share Target)

`manifest.json` объявляет `share_target` — установленное на телефон/ПК
приложение появляется в системном меню «Поделиться» других приложений
(например, браузера, где читаешь документацию). Выделил слово/фразу →
«Поделиться» → Wordbook → текст сразу подставляется в строку ввода
(`app.js`, `handleIncomingShare()`), но не отправляется на перевод
автоматически — можно поправить перед отправкой. Поддерживается только в
Chrome/Edge на Android и десктопе для установленных PWA; Safari на iOS
Web Share Target пока не поддерживает.

## Статусы записи

Каждая запись имеет один из четырёх статусов, их можно менять из меню «⋯»:

| статус       | что значит                              |
|--------------|------------------------------------------|
| `learning`   | учу — только что добавил, ещё не разобрался |
| `read`       | прочтено — видел в тексте, разобрался, но не закрепил |
| `learned`    | изучено — уверенно знаю                  |
| `reviewing`  | вспоминаю — раньше знал, надо повторить  |

Статусы — это фильтр, а не жёсткий процесс: пользователь сам решает, когда
переключать запись между ними, приложение ничего не форсирует
автоматически (никаких интервальных повторений и т.п. в MVP — это уже
следующий шаг, если понадобится).

## Поиск и фильтрация

- Фильтр по статусу — чипы над списком, ровно один активный одновременно
  (или «все»).
- Поиск — по подстроке, ищет одновременно и в исходном тексте, и в
  переводе (`ILIKE` по обоим полям на бэкенде). Debounce 300 мс на
  фронтенде, чтобы не долбить API на каждое нажатие клавиши.
- Оба фильтра применяются на сервере (`GET /api/entries?search=&status=`),
  а не на клиенте — так поиск работает по всей базе, а не только по тому,
  что успело подгрузиться.

## Редактирование и удаление

Через «⋯» в правом верхнем углу карточки:
- **Изменить** — правит перевод (сейчас — простой `prompt()`, в проде
  стоит заменить на нормальную инлайн-форму).
- **Удалить** — с подтверждением, `DELETE /api/entries/:id`.
- Смена статуса — там же, отдельным блоком кнопок.

Для записей, которые ещё не синхронизировались (`pending`), эти действия
работают локально, с самой очередью в IndexedDB, а не с сервером.

## Наполнение словарей (сервер + устройство)

Реализовано автоматически, в обе стороны сразу:

- **Сервер.** При каждом старте backend (`server.js`) вызывает
  `ensureDictionary()` (`scripts/ensure-dictionary.js`). Если таблица
  `dictionary` пустая — скачивает исходные данные и грузит их через
  `import-dictionary.js`; если уже наполнена — почти мгновенно
  пропускает шаг. Управляется флагом `AUTO_IMPORT_DICTIONARY` в
  `backend/.env` (см. `docs/INFRA.md`).
- **Устройство.** При первом запуске приложения, пока в IndexedDB ещё
  пусто, `app.js` (`ensureOfflineDictionary()`) сам обращается к
  `GET /api/dictionary/device-bundle` и кладёт результат через
  `WordbookDB.bulkImportDeviceDictionary()`. Если бэкенд ещё не успел
  собрать бандл или сети нет — просто пробует при следующем запуске.

Оба бандла (большой для Postgres и компактный для устройства) строит один
и тот же скрипт — `scripts/fetch-source-dictionary.js`, — из одного и
того же открытого источника (см. `INFRA.md`): в компактный бандл на
устройство попадает только первые N слов на каждый файл-источник, а
источники уже отсортированы по частотности, так что это и есть
"топ-N частотных слов" без отдельного частотного словаря.
